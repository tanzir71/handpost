# Relay Architecture Decisions

## 2026-07-11 — Browser patching strategy
Relay uses stock Playwright with real installed Chrome plus explicit webdriver/CDP self-tests instead of depending on an unverified stealth fork. Persistent headed Chrome profiles and human-scale operation remain the primary safety controls. A maintained drop-in patch may be adopted later only after its provenance and Electron compatibility are verified.

## 2026-07-11 — Bluesky browser-first behavior
Although Bluesky offers an open API, Relay keeps the browser adapter as the default so all platforms exercise the same engine and proof pipeline. An API fallback is deliberately not implemented because it would violate the product's local browser-automation premise.

## 2026-07-11 - Target-specific publishing data

Per-platform wizard fields and media alt-text overrides are stored in `post_targets.options_json`; probed media byte size is stored in `media.size_bytes`. Keeping these values with the target and media rows makes drafts, retries, archive round-trips, and platform validation deterministic without adding platform-specific tables.

## 2026-07-11 - Persistent browser lifecycle

The scheduler reuses one named persistent context per platform across a queued publishing batch, then closes it when the global queue becomes idle; application shutdown also drains the queue and closes any login/manual contexts. This satisfies the idle-memory target while retaining the persistent on-disk Chrome profile across batches. MockSocial uses an expiring persistent cookie so restart survival is covered without relying on session-only cookie behavior.

## 2026-11-18 - Rebrand implementation, browser choice, renderer base

The app now runs as Handpost (package `handpost`, productName `Handpost`, app id `com.tanzir.handpost`). Because Electron derives the user-data folder from the product name, first start copies `<appData>/relay-scheduler` into `<appData>/Handpost` (database via a staged copy with its WAL, then browser profiles, media and artifacts) and re-points stored absolute paths; the old folder is never modified, and a marker file makes the import run once (`src/main/migrate-legacy.ts`). Archives are written as `handpost.json` and old `relay.json` archives still import.

Playwright can drive Microsoft Edge as well as Google Chrome. `HANDPOST_BROWSER` (chrome | msedge | chromium) chooses explicitly; otherwise installed Chrome is used, then Edge, which every Windows machine has. Either way Handpost uses its own per-platform profile directory, never the person's everyday browser profile: borrowing those cookies would break the "manual login, no cookie export" rule, and current Chromium browsers refuse automation of the default profile anyway.

The renderer is built with `base: './'` because Electron loads it from `file://`; root-absolute `/assets/...` URLs would leave a packaged app with a blank window. Tray icons are PNGs (Electron's nativeImage does not decode SVG), generated from `assets/brand/*.svg`.

## 2026-11-18 - H0 hygiene: line endings, formatting scope, row types

`.gitattributes` normalizes every text file to LF in the repository and the working tree (`* text=auto eol=lf`), so Windows checkouts with `core.autocrlf=true`, WSL and CI all see identical bytes and Prettier's `--check` behaves the same everywhere. The one exception is `*.cmd`/`*.bat`, which stay CRLF because cmd.exe mis-parses labels and multi-line blocks in LF batch files. Prettier formats `src/`, `tests/`, `scripts/` and the root config files; DOM fixtures (captured pages), `site/`, `docs/`, `examples/` and `schema/` are deliberately excluded so formatting never changes test inputs or public contract files. Renderer props are typed with `Fields<Row, Required, Optional>` (a `Pick` plus an optional `Pick` over the SQLite row types in `src/shared/rows.ts`) rather than full rows, so each component states exactly which columns it reads and tests can pass only those.

## 2026-11-18 - H2 inbox service: choices the protocol leaves open

`004_inbox.sql` adds three things beyond the handoff's draft: `inbox_items.replaced_at` (receipts report it), `inbox_items.root` and an `inbox_files` log (one row per handled file: accepted, duplicate, rejected, cancel). Duplicates never create an item row (the id is the primary key), so the log is what lets the Inbox screen show "Duplicates" and Settings show "Writers seen", and it is how read-only roots (the H9 Git clone) remember which files were already handled.

An id whose only history is a rejection or a wait for media (no post was ever created) is not "used": a corrected file with the same id is processed as new instead of hitting `duplicate_id`, because writers are told to fix and resend. Conversely, a rejected file whose id belongs to a live post (`duplicate_id`, `already_publishing`, an invalid replacement) never overwrites that post's receipt — the receipt keeps describing the post that will actually go out, and the writer's feedback is `rejected/<file>.error.json`.

The idempotency hash excludes `handpost` as well as `on_conflict`, because `handpost` is optional inside batches and the same post must hash the same alone or in a batch. `mode: draft` posts carry no time (they are never scheduled), while held posts keep resolved times on `draft` targets; those held times count as occupied queue slots so approving several held posts does not stack them on one slot. A batch with any post still waiting for media stays in the inbox; posts in it that were already committed come back as harmless duplicates on the next pass. When the owner rejects a held item it ends `rejected` with its targets `cancelled` and no protocol error code (the §10 codes describe file problems, not owner decisions).

The status file reports never-connected accounts as `status: "not_connected"` and includes posts made in the app in `upcoming`/`recent` under `app-<postId>`, so writers avoid repeating them too. Inbox posts may only target MockSocial when `HANDPOST_INBOX_MOCK=1` (development smoke runs and tests). On Windows, replacing a receipt that a reader, indexer or antivirus has open fails with EPERM, so atomic renames retry for up to ~5 s; a worker-thread reader test proves no partial file is ever visible. Posts from IPC, CSV and the inbox are all written by `src/main/posts/create.ts`, which also gives `queue-post` the 09:30 / 17:30 default slots instead of throwing when an account has none.

## 2026-11-18 - H3/H4 renderer: tokens, routing, demo data, screen behaviour

All colour lives in `src/renderer/styles/tokens.css`; a unit test fails on any hex or `rgb(` literal elsewhere in `src/renderer`, and another computes WCAG contrast for every text/background pair the components use, in both themes, plus white monograms on each platform hue (the hues are fixed tokens, darkened where needed to reach 4.5:1). Fonts are the latin `.woff2` subsets from the `@fontsource` packages, copied into `src/renderer/assets/fonts/` with their OFL licences — no font package is a runtime dependency and nothing is fetched. The theme is the `theme` setting (system/light/dark) applied as `data-theme` on `<html>`, cached in localStorage only to avoid a wrong-theme first paint.

The renderer uses hash routes (`#/inbox`, `#/compose/12`, `#/settings/automation`, dev-only `#/__gallery`) so it stays a static file under `file://`. In a plain browser (Vite, `scripts/verify-ui.ts`, landing-page screenshots) `window.handpost` is absent and an in-memory demo API with realistic sample data stands in; it never touches a network. The Inbox's receipt panel opens only when a row is selected (the list keeps full width otherwise), rows are a keyboard-navigable listbox that virtualizes above 200 rows, and filters/search persist in sessionStorage. Compose's schedule bar is a segmented control (Next free slot / Exact time / Post now) driving one primary button, with *Add to queue* still one click away; Exact time defaults to an hour from now in *local* time (the old default used a UTC string as local time). Destructive actions use an in-page confirm popover. The Auto-schedule trust-boundary explanation is shown once and remembered as `inbox.trustConfirmed`. Vitest gets its own config (merging the Vite one) with a 60 s teardown, because each test fork is an Electron-as-Node process that can be slow to exit on Windows under a full parallel run.

## 2026-11-18 - H5 schema generation and writer guides

`schema/handpost-post.v1.schema.json` is now generated from the zod schema by `npm run schema` (zod-to-json-schema, `$defs` named after the zod parts) and a unit test fails if the committed file differs, so the published schema can no longer drift from what the app enforces. Two zod refinements (unique `platforms` and `labels`) are restated as `uniqueItems` in the generator, and the top-level post is emitted as `post` + `required: [handpost]`, which is exactly the zod `topPost`. Cross-field rules (override keys must be targeted platforms; thread/first_comment/options only where a platform supports them) stay app-side and are documented in the guides. The SKILL.md template block is now a complete valid file with placeholders as YAML comments, so a test can validate every `handpost: 1` block (including heredocs) in SKILL.md, the Codex AGENTS.md and AUTOMATION.md against both the JSON Schema and zod. `npm run inbox:smoke` exercises examples + a MockSocial post end to end in a temp folder under Electron-as-Node (better-sqlite3 is built for Electron).

## 2026-11-18 - H6 live readiness: identity, Rehearse, browser detection

Each platform's `selectors.ts` exports an own-profile link (`identity`); after a manual login (and opportunistically after any successful session check) Handpost reads its href and stores `accounts.handle` and `accounts.profile_url` via pure per-platform rules in `adapters/identity.ts`. Verification opens the stored profile URL; without one it starts from the platform's home page and follows the profile link, so no `/me`-style placeholder URL remains. A profile URL the owner typed is never overwritten automatically, and Facebook is never auto-captured, because the link Facebook shows is the personal profile while Handpost posts as a Page. Pasted URLs must be HTTPS on the platform's own domain.

Rehearse is a publish with `{ rehearse: true }`: the factory returns right after the last pre-submit step (screenshot the filled composer, Escape, confirm Discard, leave for `about:blank`), and the only function that builds the submit locator throws when called during a rehearsal — two independent guards. Contract tests run a rehearsal on every platform fixture with both an interaction-level and an in-page (navigation-proof) click detector on the submit element. A rehearsal runs on the scheduler's one-at-a-time queue in a visible window and is recorded as a `publish_attempts` row with outcome `rehearsal` on a hidden post/target with status `rehearsal`, which the queue, calendar, composer and status file all exclude, while History shows it. Image platforms rehearse with a generated blank PNG; video platforms ask the owner to pick a video. Browser detection reads the installed version without launching (Windows: the version folder beside the exe; macOS: Info.plist; Linux: `--version`), re-checks at most once a minute, and both "not installed" and Playwright's missing-channel launch errors put targets in `needs_attention` with `chrome_missing` instead of failing them.

## 2026-11-18 - H7 packaging and releases

electron-builder builds a per-user NSIS installer (no admin, Start-menu shortcut, no desktop shortcut by default), an unsigned universal dmg and an x64 AppImage into `release/`. Migrations stay real files next to the bundle and are listed in `asarUnpack` together with `better-sqlite3` (rather than being inlined), because the boot code already reads them from `__dirname/migrations` and unpacked files keep them inspectable. `electron` moved to devDependencies (electron-builder requires it), which made tsup bundle the npm `electron` wrapper into the main process — a packaged app then re-launched itself forever trying to "download Electron"; `tsup.config.ts` now marks `electron` external, and renderer-only packages are devDependencies too. `publish: null`, no blockmap, no updater: the About tab's "Check releases" only opens the browser. Icons are rendered from `assets/brand/handpost-app-icon.svg` by `npm run icons` (Playwright screenshots packed into PNG-compressed `.ico`/`.icns`, no image library). `HANDPOST_DATA_DIR` / `HANDPOST_FOLDER` let a smoke run point the packaged app at throwaway folders (and skip the legacy import so no real data is ever copied); `npm run smoke:packaged` uses them. The release workflow builds on `v*` tags for Windows, macOS and Linux after `npm run check` and attaches the files to a draft release that the owner publishes.

## 2026-11-18 - H8 site, H9 remote Git source, H10 audit and engine race

The site is plain static HTML/CSS with the app's tokens and fonts copied in (a verifier fails if `site/styles.css` drifts from `tokens.css`), relative URLs only, and the Pages workflow copies `schema/*.json` in at deploy time (`npm run website:verify` does the same locally; `site/schema/` is git-ignored). Download stays "Coming soon" until the first release exists.

The optional Git source clones one repository into `Handpost/.sources/<repo>/` with the system `git` via `execFile` (arguments after `--`, `GIT_TERMINAL_PROMPT=0`, URL allow-list of https/ssh/scp-style/file), pulls with `--ff-only` every five minutes and on settings changes, and is fed to the inbox as a read-only root whose processed state is the `inbox_files` log (content hash + path), so files in the clone are never moved or re-posted. Receipts for that root's ids are committed and pushed only when "Push receipts back" is on.

`src/main/inbox/audit.ts` checks the invariants writers depend on (one item per post, stored state equals target-derived state, receipt on disk matches the database, no orphan receipts); a seeded test drives accept/duplicate/replace/approve/reject/publish/fail/cancel and then audits, and a seeded mutation fuzzer feeds 150 malformed files (including `__proto__` keys) and asserts no throw, no double post and no prototype pollution. Running the e2e suite under heavy machine load exposed a real race in `BrowserEngine`: a context's late `close` event deleted whatever context was registered for the platform, so the next post could launch a second persistent context on the same profile without the session. Close handlers now only forget their own context, and launches/closes are serialized per platform. Vitest's default test/hook timeouts were raised (Electron-as-Node forks on a busy Windows machine), without changing any assertion.

## 2026-11-18 - H10: handpost-mcp, resuming after login, quiet smoke runs

The backlog MCP server is a single standalone file (`src/mcp/server.ts` → `dist/mcp/server.cjs`, zod bundled) speaking newline-delimited JSON-RPC over stdio by hand rather than through an SDK dependency; it implements `initialize`, `ping`, `tools/list` and `tools/call` and nothing else. Its five tools only validate and write inbox files atomically (via `inbox/.tmp/` + rename) and read receipts/status, as D2 requires, and it refuses invalid posts before writing (same zod schema and cross-field rules the app uses, media must already be inside `inbox/`). Logging in again now puts that platform's `needs_login` targets back into the queue (jittered, at least a minute out), except those more than two hours late, which become `needs_attention: overdue` — the same never-post-stale-content rule as startup. `HANDPOST_QUIET=1` suppresses desktop notifications and the login-item call for smoke runs, because on Windows Electron registers a Start-menu shortcut the first time a toast is shown; the installer test (silent per-user install to a temp folder, smoke against the installed exe with throwaway folders, silent uninstall) leaves no trace.

## 2026-11-18 - H3/H4: aligning the screens with the Figma frames

The frames are the source of truth for layout and wording, but copy that would be false in this build was not copied: media stays inside `inbox/` (the frame says `Handpost/`), the Next banner does not claim “Chrome closed until then” because the renderer cannot know it, and the frozen-account reason says “Detection event <time>” because the breaker stores timestamps, not the checkpoint text. Two controls were kept beyond the frames because removing them would remove features: *Open draft* (shown only when drafts exist) and the collapsed *Fingerprint check* note in the Accounts banner. Facebook Page, YouTube Shorts and Pinterest are hidden under *Add platform* until they are connected, matching the frame's six cards.

*Pause publishing* is a plain boolean setting (`publishing.paused`) read at the top of `Scheduler.tick`, so it survives restarts and needs no new state. *Publish now* refuses while paused rather than queuing something that would not run. Resuming re-runs `handleOverdue`, so a long pause cannot release a backlog of stale posts: anything more than two hours late becomes `needs_attention: overdue`, the same rule as after the app was closed. Rehearse and *Retry verify* still work while paused because neither can submit.

The frame's *Retry verify* exposed a real hazard: `retry` on an `unverified` target rescheduled a full publish, and the post had in fact been submitted, so it could appear twice. `Scheduler.reverify` runs on the same concurrency-one queue, refuses non-`unverified` targets, frozen platforms and missing browsers, checks the session, runs only `adapter.verify` inside a step reporter and records a normal attempt. The Queue offers it instead of *Retry* for unverified rows; *Retry* remains for failed and needs-attention rows.

The Queue is one chronological agenda grouped by day, as in the frame, instead of a separate “Needs attention” group: today shows every row including published ones, earlier days keep only rows that still need the owner, and History holds the rest. Rehearse state moved from each card up to Accounts so *Rehearse all* can run the connected platforms one after another and report a summary; video platforms still ask for a file each time. Compose's first-comment fields come from `FIRST_COMMENT_PLATFORMS`, which a test keeps equal to the adapters that configure a `comment` step. Landing-page shots are rendered with the `en-GB` locale so dates and the 24-hour clock match the frames; the app itself follows the system locale.

## 2026-11-18 - H10: Playwright loads on first use

`npm run perf` measures the built app the way an owner meets it: Playwright's Electron driver launches `dist/main` with throwaway `HANDPOST_DATA_DIR`/`HANDPOST_FOLDER` and `HANDPOST_QUIET`, waits for the Inbox heading, idles five seconds and sums `app.getAppMetrics()` per process type (median of three runs; the first run after a reboot is a true cold start and is reported, not hidden). The main process was carrying a 39 MB JS heap because `engine/browser.ts` imported Playwright at module load, although most sessions never open a browser. `BrowserEngine.context` now does `await import('playwright')` on first use (types stay a type-only import), which brought the main heap to 8 MB, the idle working set from 447 to 391 MB and the first window from 843 to 610 ms. The packaged app already loads chokidar through the same dynamic `import()` from the asar, so no packaging change was needed. The remaining footprint is Electron's own (GPU ~130 MB, renderer ~95 MB, network utility ~50 MB).

## 2026-11-18 - H7/H8: the first tag stays a draft; Pages must build from Actions

`v0.2.0-rc.1` is a release-candidate tag on an app whose `package.json` says `0.2.0`, so the installers are named `0.2.0`; the `-rc.1` lives only in the tag and the draft's title, and the owner can publish the same draft as the final 0.2.0 or tag again after the live test. `release.yml` only ever creates a *draft*, so pushing a tag cannot ship anything to users by itself. The repository's Pages setting predates `pages.yml` and is the legacy branch build of `master` `/`; in that mode GitHub's `pages-build-deployment` runs on every push and wins over the workflow's deployment, publishing the repo-root `index.html` instead of `site/`. The fix is the Pages source setting (“GitHub Actions”), not a root `index.html` redirect or a `gh-pages` branch, so the deployed site stays exactly what `npm run website:verify` checked.
